## F. Causas prováveis (ordenadas)

1. **SSE consumer `ProcessingStatus` is defined but never mounted in the UI** — `grep -rn "ProcessingStatus" apps/web` shows zero importers. `apps/web/app/(dashboard)/documents/[id]/page.tsx` does NOT include it; `field-panel.tsx` has no SSE subscription. After the EXTRACTING stage completes and writes `supplier`/`supplierNif` to the DB, the front-end never refetches unless the user navigates or clicks "Re-extrair". The TanStack `useDocumentBundle` cache has `staleTime: 30_000` (`use-document-detail.ts:178`) — for up to 30 s after a successful query, fresh DB writes are invisible to the page.
   - **Evidência**: `apps/web/app/(dashboard)/documents/[id]/page.tsx` (no import of `ProcessingStatus`), `use-document-detail.ts:178` (`staleTime: 30_000`).

2. **SSE payload for EXTRACTING carries no extracted fields** — `processing.service.ts:205-215` emits only `{ stage, status, completedAt }`. Even if a consumer WERE mounted, it would not learn supplier NIF / name from SSE. The fields live in the queue event `document.extracted` (`extraction.service.ts:1248-1260`) — a separate channel the SSE doesn't mirror.
   - **Evidência**: `processing.service.ts:205-215`, `extraction.service.ts:1280-1312` (queue event carries `extractedFields` but the SSE bridge skips it).

3. **Vision chain can fail silently across all 5 configured providers** — `vision.service.ts:567` returns `null` after the chain exhausts. `runAiOrRegexPath` (`extraction.service.ts:1484-1532`) then either marks `needs_review` (image-only) or promotes regex + a generic warning (everything else). The pipeline keeps advancing EXTRACTING → ENRICHING → ROUTING → COMPLETED as if nothing went wrong. Operator has to dig into `metadata.extraction.warnings` or the `needsReview` flag to learn the AI failed.
   - **Evidência**: `vision.service.ts:552-568` (chain-exhausted returns null), `extraction.service.ts:1484-1532` (silent fallthrough).

4. **MiniMax primary has no per-attempt timeout below 60 s but aborts anyway on slow networks** — `callMinimax` uses `effectiveTimeoutMs = max(timeoutMs, 60_000)` (line 1614) but the upstream socket can sit in TCP retry for the full 60 s × 2 attempts = **120 s wall-clock worst case**, on top of OpenRouter + direct Gemini fallbacks (each up to 30 s × 3 attempts = 90 s, plus the 50 s escalation call) = total ceiling ≈ **260 s** before `analyze()` returns. The SSE consumer's 3-second watchdog fires after just 3 s (`SSE_POLL_TIMEOUT_MS = 3_000`), so the consumer (if mounted) would already have given up and switched to polling by the time MiniMax returns. Combined with cause #1, the operator sees `polling` for ~4 minutes before the doc state finally updates — and even then only via the 4 s poll.
   - **Evidência**: `vision.service.ts:1614` (60 s × 2), `:1325` (30 s × 3), `:691-696` (50 s escalation), `processing-status.tsx:51, 92`.

5. **OpenRouter primary + escalation model may be quota-exhausted on real phone photos** — the doc comments at `vision.service.ts:369-389`, `:1240-1249`, `:1459-1466`, `:2090-2093` describe real-world reliability problems with the OpenRouter route: 2/3 truncation rate, gemini-2.5-flash "404 on Google's API (only gemini-3.6-flash is offered and that is also out of quota)", and that the user picked MiniMax as primary specifically because of these. Even with MiniMax key set, a quota-exhausted direct Gemini or OpenRouter means the chain falls through without delivering authoritative `total` / `supplier` — leaving an empty result the regex path can't fill on image-only docs.
   - **Evidência**: `vision.service.ts:369-389` (provider-priority comments), `:2091-2093` (corrupt-numerics patterns), `:2164-2166` (total > 1_000_000 gate).

6. **`Anthropic` not configured → Copilot chat silently degrades to `localFallback` in production** — `apps/api/.env` has no `ANTHROPIC_API_KEY`; `LlmProvider` constructor (`llm-provider.ts:42-67`) sets `hasAnthropicKey = false`, logs the warning, and `chat()` returns `{ provider: 'local-fallback' }` for every call (`llm-provider.ts:120-124`). The fallback's last paragraph even says "Define ANTHROPIC_API_KEY no .env para usar o modelo Opus 5 real" (`llm-provider.ts:267-269`) — the operator sees this in chat output. Any chat that depends on real Opus 5 reasoning is silently downgraded. If the operator hits the Copilot expecting real answers and gets the deterministic template, they may assume the whole pipeline is broken.
   - **Evidência**: `llm-provider.ts:42-67`, `:120-124`, `:267-269`, `.env` (no `ANTHROPIC_API_KEY`).

7. **Image-only document with no AI provider key configured writes `needs_review` but SSE event doesn't carry it** — `extraction.service.ts:1113-1123, 1159-1216`: `writeNeedsReviewMarker` updates the Document row in a separate transaction, sets `processingStatus='EM_REVISAO'` and a flag — but the `events.emit` for that comes only via the eventual ROUTING / COMPLETED / FAILED transitions. There's no dedicated `processing.needs_review` SSE event. So an operator watching the SSE for "the AI succeeded or failed" sees only generic stage transitions, never learns `needs_review` happened.
   - **Evidência**: `extraction.service.ts:1159-1216` (`writeNeedsReviewMarker` doesn't emit any SSE event), `processing.service.ts:517-529` (ROUTING event has no `needsReview` field).

8. **`Sonnet 4.6` / `gemini-2.5-pro` escalation model may hit a different quota than the primary** — `vision.service.ts:683-700` (`maybeEscalate`) only triggers when the primary IS `openrouter` and the primary result is "parseable but unusable". On MiniMax primary (the current priority per `:405-411`), the escalation is BYPASSED entirely (`:667-670` comment: "burning an extra escalation call before that would just delay the chain's natural progression"). When MiniMax returns a parseable-but-corrupt `total`, the chain falls straight to OpenRouter (which may also be degraded) instead of one-shot retrying on gemini-2.5-pro. This is by design, but on real phone photos with corrupt QR blocks, it means the strongest model never gets the chance.
   - **Evidência**: `vision.service.ts:679-689` (escalation gate), `:660-670` (rationale comment).

9. **`Sonnet 4.6` direct call (`callAnthropic`) is never reached from the auto-chain** — `buildProviderChain` (`vision.service.ts:580-597`) explicitly excludes Anthropic from the chain even when it has a key — Anthropic only runs if the user pins `preferredProvider='anthropic'`. So in normal uploads Anthropic is opt-in only, even though `ANTHROPIC_API_KEY` may be the strongest key set. Combined with cause #6, this means the operator may have set the key but the pipeline still routes MiniMax → OpenRouter → direct Gemini.
   - **Evidência**: `vision.service.ts:580-597`, `:399-403`.

10. **3-attempt OpenRouter retry has no backoff** — `callOpenRouterWithModel` retries immediately on abort / parse failure (line 1328-1433). On a quota-429 or transient DNS failure, hammering the upstream 3× in ~90 s makes the situation worse and inflates cost. No `await sleep(...)` between attempts.
    - **Evidência**: `vision.service.ts:1325-1433` (loop without backoff).

11. **Front-end polling fallback uses `authedFetch('/documents/:id')`** — `processing-status.tsx:191-202`. Each poll is a full document read, not a status-only endpoint. Combined with cause #1 (the consumer isn't mounted) this isn't a live bug, but if the consumer is ever wired in, the polling will hammer the doc endpoint at 4 s intervals for up to 4 minutes — ~60 requests per slow doc.
    - **Evidência**: `processing-status.tsx:51, 191-202`.

12. **`processing-stage.completed` for EXTRACTING is emitted BEFORE the DB write finishes** — `processing.service.ts:204-215` emits the EXTRACTING event AFTER the `tx.document.update({ processingStatus: 'EXTRACTING' })` commit, but BEFORE `this.extraction.enqueue(...)` (line 218-222) has actually written `supplier` / `supplierNif` to the row. So if a future SSE consumer refreshes the doc detail on this event, it'll race the write and may still see the old supplier. Not currently exploitable (cause #1), but a latent bug for any future fix.
    - **Evidência**: `processing.service.ts:204-222` (emit then enqueue).
